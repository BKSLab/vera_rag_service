## 1. Цель и границы

Цель — проверить после выкладки:

1. закрытие `B-01…B-07` на реальном production-корпусе;
2. отсутствие регрессий ранее зелёных retrieval/golden-кейсов;
3. стабильность маршрутизации, query expansion и reranker;
4. корректность пользовательского ответа и frontend-поведения;
5. сопоставимость latency с baseline до изменений.

- используются только контролируемые синтетические запросы;
- независимые Agent-кейсы выполняются в новых сессиях;

- production-сервисы, конфигурация, корпус и данные во время серии не меняются;
- техническую недоступность RAG намеренно не создаём на production;

## 4. Правила фиксации результатов

Для каждого запуска записываем:

- точный пользовательский текст без последующего редактирования;
- время, поверхность (`Admin`/`Chat`) и номер повтора;
- `session_id`, `request_id`, `search_logs.id` — что доступно;
- Agent route и точный tool-query;
- `query_variants`, expansion/reranker status;
- финальные `document_id + section_number`, позицию целевой нормы;
- полный смысл ответа, названные основания и запрещённые домыслы;
- frontend-наблюдения и ссылку на screenshot/trace/log;
- latency и результат `PASS` / `FAIL` / `BLOCKED`.

Правила серии:

1. Новый независимый Chat-кейс — только новая сессия.
2. История сохраняется только в явно многоходовых кейсах.
3. Неудачный первый запуск не заменяется удачным повтором: фиксируются оба.
4. `route_reason` и `candidate_sources` не являются hard gate: в БД их нет.
5. Технический сбой не имитируется остановкой production-сервиса.
6. Полные ответы и screenshots с потенциальными пользовательскими данными не
   добавляются в git; в отчёте остаются обезличенные наблюдения.
