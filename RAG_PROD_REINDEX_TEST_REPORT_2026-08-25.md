Предлагаемое закрытие B-01:

1. До обращения к query-expansion LLM детерминированно распознавать режим запроса: `reference_only`, `reference_with_question` или `natural_language`.
2. Для `reference_only` LLM expansion не вызывать: использовать исходную строку и, при необходимости, только детерминированную нормализацию сокращений без раскрытия содержания нормы.
3. Передавать режим и разобранные реквизиты нормы в retrieval, чтобы добавить отдельную exact-reference ветку по документу/статье; обычный hybrid retrieval оставить как резервный канал.
4. Инструкцию «для голой ссылки не создавать смысловую переформулировку» также добавить в промпт как второй уровень защиты, но не использовать решение LLM как единственную safety-границу.
5. Сохранять `query_mode` в диагностике/search log и показывать его в тестовой админке.
6. Регрессионно проверять, что для голой ссылки expansion-клиент не вызывается и в поисковые варианты не попадает содержание нормы, отсутствующее в исходном запросе.

Предлагаемое закрытие B-05:

1. Для самодостаточного сообщения первого хода передавать в RAG исходный пользовательский текст без свободной переформулировки Agent Service: собственный query expansion уже выполняется внутри RAG.
2. Разрешать Agent Service дополнять tool-query только для несамодостаточных продолжений, когда объект действительно восстанавливается из сообщений этой же сессии.
3. Ввести проверяемое правило: в tool-query не появляются признаки пользователя, юридические факты, нормы или числа, которых нет в текущем сообщении либо явно установленной истории.
4. Добавить регрессионные пары общего и явно специализированного запроса: без слов об инвалидности tool-query остаётся общим; при прямом указании инвалидности этот признак сохраняется.
5. Логировать исходное сообщение рядом с фактическим tool-query и причину контекстного дополнения, чтобы drift обнаруживался автоматически.

Предлагаемое закрытие B-07:

1. До разрешения неполной реплики программно проверять наличие хотя бы одного предыдущего пользовательского/ассистентского хода в checkpoint текущего `session_id`.
2. При отсутствии антецедента не передавать модели инструкцию трактовать фразы вида «а если откажет» как полноценный follow-up: вернуть короткое уточнение, в чём именно отказал работодатель.
3. При наличии истории дополнять tool-query только предметом, буквально установленным этой историей, без признаков из общей специализации Веры.
4. Добавить trace-атрибуты `context_resolution=none|history|clarification` и идентификатор сообщения-источника; автоматически проверять, что `history` невозможен при пустой истории.
5. Запретить генератору объяснять своё решение ссылкой на «контекст диалога», если в фактическом input отсутствовали предыдущие сообщения.

#### Q-09 — архитектурная оценка фильтра темы

- Первый предполагаемый прогон фильтра (`id=97`) фактически имел `topic=NULL`: строка `quota` в форме была HTML-placeholder. Полученная выдача была обычным повтором Q-05 и не является тестом фильтра.
- Production-справочник содержит восемь тем: `дискриминация`, `квотирование`, `охрана труда`, `приём на работу`, `рабочее место инвалидов`, `трудовые права`, `трудоустройство`, `увольнение`.
- Метки назначены на уровне документа и копируются всем его чанкам. У ТК РФ и обоих федеральных законов список пуст; оба больших документа судебной практики имеют все восемь тем; приказ № 685н имеет четыре, постановление № 709 — четыре темы.
- Поэтому hard-filter `квотирование` исключил бы статью 38 ФЗ-565 — основной первичный источник — и пропустил бы любой чанк обоих судебных документов независимо от его реального содержания. Это формально корректная exact-match фильтрация, но семантически плохой режим юридического поиска.
- Agent Service не может и не должен выбирать тему: фактическая MCP-прокси имеет сигнатуру `vera_rag_kb(query: str)` и передаёт серверу только `{'query': query}`. - Решение: снять Q-09 с end-to-end приёмки. Темы оставить только как административную таксономию/аналитические метки, если для них есть отдельный потребитель; иначе удалить. Если тематический сигнал когда-либо понадобится поиску, проектировать его как soft boost по меткам конкретных секций, а не как исключающий фильтр всего корпуса.

#### Q-03 — сокращённая ссылка на пункт, часть и статью

- Query expansion фактически раскрыл `п. 2 ч. 1 ст. 81 ТК РФ` в смысловую формулировку о сокращении численности или штата. Раскрытие оказалось правильным, однако выполнено до retrieval: модель получила только исходный запрос и восстановила содержание нормы из собственных знаний, а не из production-корпуса.
- Для простого запроса промпт query expansion требует вернуть исходный текст без изменений как `sub_question` и не более одной юридической переформулировки. В этом прогоне поэтому существовали две независимые поисковые ветки: точная ссылка и её смысловое раскрытие; исходный запрос не был заменён.
- Техническое наблюдение: `_flatten_variants()` формирует список только из ответа LLM и не добавляет `original_query` безусловно. Схема также не проверяет равенство `sub_question` исходному тексту. Следовательно, сохранение точной формулировки сейчас обеспечивается инструкцией модели, но не программной гарантией. Кандидат на hardening: принудительно сохранять исходный запрос первой веткой и дедуплицировать добавленные LLM-варианты.
- Grounding-риск query expansion: требование промпта «не добавлять новых фактов» не предотвращает расшифровку голой ссылки на норму по памяти модели. При ошибке или устаревшем знании такая смысловая ветка способна направить часть поиска не к той норме. Для распознанных точных ссылок безопаснее до retrieval создавать только исходную и детерминированно нормализованную ветки (`п.` → `пункт`, `ч.` → `часть`, `ст.` → `статья`, `ТК РФ` → полное название), а смысл нормы получать уже из найденного текста.
- Финальный top-1 — основной фрагмент статьи 81, содержащий пункт 2 части первой; top-2 — продолжение той же статьи с правилом о предложении другой работы.

- Основной фрагмент статьи 81 имеет RRF-score `0.0214` и находился на одной из позиций 15–16 RRF; reranker поднял его на финальную позицию 1. Продолжение статьи 81 имело RRF-score `0.0246` (RRF #7) и стало финальным #2.

#### Q-12 — вопрос вне корпуса

- Запрос о порядке оформления заграничного паспорта не относится к трудовому праву и отсутствует в production-корпусе.
- Hybrid retrieval сформировал RRF candidate pool из `85` формально похожих, но нерелевантных чанков; reranker отклонил их все, финальная выдача пуста. Это ожидаемое поведение `no_relevant`.
- Вера не стала отвечать из общих знаний, то есть основное safety-требование соблюдено.
- Проверка Postgres показала только одну строку запроса про паспорт (`search_logs.id=70`, `reranker_status=no_relevant`, `result_count=0`) — это админский прогон. Отдельной строки от Веры нет.
- Backend-логи за тот же интервал содержат единственный `POST /search` в `18:31:35–18:31:39`, найден один результат; по времени и результату это end-to-end запрос Веры про отпуск (`search_logs.id=69`). Для вопроса про паспорт после админского прогона входящего `POST /search` и ошибки поиска нет.
- Вывод: Вера не пыталась обратиться к RAG для вопроса про паспорт и при отсутствии фактической ошибки самостоятельно сформулировала сообщение о техническом ограничении доступа. Это B-03 в Agent Service. Допустимый ответ без вызова инструмента — честное указание на предметную область; при успешном пустом поиске — отсутствие релевантных данных; сообщение о временной недоступности допустимо только при реальной ошибке инструмента.
- Проверка кода `vera_agent_service` подтвердила первопричину B-03:
  - кодовый guard `is_probably_factual_or_legal_question()` проверяет только ограниченный список трудовых/правовых ключевых слов; слово `паспорт` и общие признаки фактического вопроса в нём отсутствуют;
  - если intent-модель не вызывает RAG и guard не срабатывает, `analyze_intent` возвращает пустое обновление, а граф направляет запрос в `generate_direct`;
  - `generate_direct` не получает отдельного признака `out_of_scope`/`search_not_called` и всегда просит LLM сформировать текст;
  - промпт прямой ветки одновременно говорит, что при отсутствии данных нужно честно отказать, и рядом упоминает варианты «переформулировать»/«обратиться позже» для отсутствия ответа либо недоступности поиска. Не имея фактического статуса поиска, модель смешала эти случаи;
  - корректно разведённые `NO_ANSWER_INSTRUCTION` и `SEARCH_UNAVAILABLE_INSTRUCTION` существуют только в `generate_with_context`, то есть после фактического вызова RAG, куда этот запрос не попал;
  - фраза «доступ к базе знаний ограничен» в коде и шаблонах отсутствует — она сгенерирована LLM, а не возвращена техническим fallback.
- Рекомендуемое закрытие B-03: сохранять явную причину прямого маршрута (`social`/`out_of_scope`/`history_rewrite`), запрещать прямому генератору утверждать недоступность поиска без `search_unavailable=True`, а для `out_of_scope` возвращать детерминированный честный ответ либо отдельную однозначную инструкцию. Отсутствие `tool_call` нельзя использовать как неразличимый общий маршрут для приветствия, непрофильного вопроса и ошибки маршрутизации.

#### A-01 — несуществующая точная норма

- Админский поиск получил исходный запрос `п. 1 ч. 1 ст. 999 ТК РФ` и LLM-вариант `Действующая редакция статьи 999 Трудового кодекса Российской Федерации`.
- Положительный результат: после reranker финальная выдача пуста — несуществующая статья не была подменена похожей нормой и пользователю не показан нерелевантный чанк.
- Размер RRF candidate pool: `98`, ниже контрольного сигнала `150`, но почти весь этот поиск является шумом для однозначной ссылки на отсутствующую норму.
- Query expansion не придумал содержание статьи 999, однако сам вызов LLM и добавление намерения «действующая редакция» для `reference_only` избыточны. Это дополнительное подтверждение необходимости детерминированного режима из B-01: сохранить/нормализовать ссылку, не раскрывая и не предполагая её смысл.
- Статус RAG-части: PASS по безопасному финальному результату; архитектурный FAIL по маршруту `reference_only`.
- Первый end-to-end прогон был ошибочно выполнен в существующей сессии. Вера ответила, что статьи 999 нет, но отдельной строки поиска после админского `id=71` не появилось. Это не используется как изолированный итог A-01, однако остаётся production-наблюдением: история влияет на маршрут, и новая точная правовая ссылка может обойти RAG (B-02).
- В повторном прогоне в новой сессии появилась отдельная строка `id=72` с исходным запросом, `query_expansion_status=ok`, `reranker_status=no_relevant`, `result_count=0`. Следовательно, в чистой сессии Вера действительно вызвала RAG и корректно получила пустой результат.
- Ответ правильно сообщил именно о том, что поиск по базе знаний ничего не нашёл, и не назвал это технической недоступностью. Это PASS относительно B-03.

Возвращённых чанков не было, поэтому утверждение о размере действующего кодекса взято не из RAG. При строгом grounding это отдельный FAIL (B-04), даже если утверждение фактически верно.

#### A-02 — ложная предпосылка о 90 днях

Этот факт действительно есть в статье 128, однако до retrieval он мог появиться только из внутренних знаний expansion-LLM. Это ещё одно воспроизведение B-01.
- Поиск вернул единственным финальным результатом статью 128 ТК РФ; целевой чанк `acf4ca0b…` занял RRF #1 (`0.0328`). Размер candidate pool: `83`, ниже контрольного сигнала `150`.

- Размер RRF candidate pool: `72`, ниже контрольного сигнала `150`. Retrieval/reranker и сохранение исключения: PASS.
- Вера корректно ответила, что при ликвидации увольнение во время больничного допускается, а в остальных случаях увольнение по инициативе работодателя в этот период запрещено. Этот текст полностью поддерживается показанными чанками.
- `search_logs` подтвердил два независимых запроса: `id=75` — админка; `id=76` — безопасный нейтральный tool-query Веры `увольнение работника на больничном при ликвидации организации`. В финальном контексте Веры находились статья 81 и пункты 23 и 50 Постановления Пленума № 2.
- Пункт 50 действительно повторяет общий запрет на увольнение в период временной нетрудоспособности и исключение при ликвидации/прекращении деятельности ИП, применительно к руководителю организации. Поэтому ссылка Веры на пункты `23 и 50` подтверждена фактически возвращёнными чанками и не является citation hallucination.
- Итог A-03: query expansion, Agent tool-query, retrieval/reranker и grounded end-to-end ответ — PASS.
